# 人类身份与房间授权

`internal/humanauth` 是独立的服务端授权模块。它默认关闭，现有 Gateway 未接入该模块。独立的本地试验进程见[本地房间观察页](local-room-observer.md)。共享 Bearer 和 observer 凭据的现有行为保持原状。

## 配置结构

下面是占位示例。该结构供后续接入使用，当前 Gateway 不读取此文件。

```json
{
  "enabled": false,
  "credentials": [
    {
      "human_id": "<稳定的人类 ID>",
      "token_sha256": "<令牌字符串的 64 位十六进制 SHA-256 摘要>",
      "expires_at": "<RFC3339 到期时间>",
      "rooms": {
        "<只读房间 ID>": {"read": true},
        "<读写房间 ID>": {"read": true, "write": true}
      }
    }
  ]
}
```

每个人使用独立的令牌，由 32 个密码学随机字节编码成无填充的 base64url 字符串。摘要针对编码后的原始字符串。服务端配置只保存摘要，配置文件应限制读权限。令牌、摘要和授权请求头都应排除在日志中。

接入时，将同一份运行配置中的共享 Bearer 和 observer Bearer 摘要显式传给 `New`。只对原始令牌值计算摘要，两者共用一个值时可传相同摘要。匹配旧凭据、重复摘要、重复人类 ID 或缺失到期时间都会使启用配置校验失败。每个房间 ID 精确匹配，`read` 与 `write` 分开授予，未列出的权限默认为拒绝。

`Authorize` 读取单一显式 `Authorization` header，结合当前服务端时间、目标房间和所请求的权限判定。成功仅返回配置中的人类 ID。发言者身份由调用方使用该 ID 绑定，正文不参与身份决定。缺失、无匹配、已过期或权限不足均返回同一拒绝结果。

## 保护房间的最小接入

1. 由 Gateway 启动配置明确列出受保护房间。启用前严格解析并校验完整配置。现有外层中间件和历史处理器都校验共享令牌，需在路由边界统一选择授权策略。受保护房间走新读检查，其余房间与路由沿用现有校验。历史列表和 HTML 导出共用一个检查点，位置在解析目标房间之后、查询持久化事件之前。在线状态和最近发言等派生信息也走此检查。
2. `/ws` 和 `/api/v1/agent/connect` 对受保护房间应在升级连接、订阅事件总线和读取回放之前检查读取权限。转发实时事件时也要确保授权仍有效。凭据到期、轮换或房间权限撤销后关闭相应订阅，后续重连重新校验。浏览器可以沿用显式携带 header 的 HTTP 轮询。
3. 先核对受保护房间的旧客户端。现有共享令牌的 observer、Agent 和桥接进程缺少独立房间身份，启用检查后可能失去该房间的读取和回放能力。需要这些客户端的房间，应先确认相应的受控身份和权限。对受保护房间拒绝时不回退到共享令牌。配置轮换应一次替换授权策略和旧令牌摘要，避免在新旧状态之间留下授权空档。

若将该模块整合到现有 Gateway，应用临时数据库和合成身份验证历史、导出、实时订阅与断线回放的访问结果一致，并覆盖凭据过期和撤权。

现有路由的审查、读租约和接线门槛见[受保护房间读路径审查](protected-room-read-audit.md)。
